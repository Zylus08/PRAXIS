# Function & Constructor Overload Resolution Semantics

**Milestone:** Project PRAXIS — Milestone M2  
**Target Specifications:** Sections 7, 12, 13  

---

## 1. Candidate Collection and Organization

In Project PRAXIS M2, function and constructor calls undergo principled overload resolution based on candidate collection, viability filtering, conversion ranking, and pairwise Pareto superiority testing.

### 1.1 Function Signatures
Every function, constructor, and method has a canonical signature ID generated by `Analyzer::signature`:
```cpp
std::string Analyzer::signature(const F& f) const {
    std::string id = f->owner.empty() ? "" : f->owner + "::";
    id += f->constructor ? "$ctor" : f->destructor ? "$dtor" : f->name.text;
    id += "(";
    for (auto d : f->params) {
        auto t = d.type;
        if (!t.reference) t.constant = false;
        id += typeName(t) + ";";
    }
    id += ")";
    if (f->constMember) id += "const";
    return id;
}
```
Functions sharing the same unqualified or qualified name form an **overload set** stored in `std::map<std::string, std::vector<std::shared_ptr<Function>>> functions`.

---

## 2. Viability Filtering

When a call expression `f(arg1, arg2, ...)` is evaluated, `Analyzer::select` filters the candidates in the overload set:
1. **Arity Matching:** Candidates whose parameter count differs from the argument count are discarded (unless a template parameter deduction succeeds).
2. **Template Argument Deduction:** For function templates, template type parameters are deduced from argument types. Candidates where deduction fails or produces conflicting types are eliminated.
3. **Implicit Object Viability:** For member functions, if the calling object expression is `const`, non-const member functions are eliminated.
4. **Parameter Viability:** Each argument expression must be convertible to the corresponding parameter type with a non-negative conversion rank (`rank >= 0`).

---

## 3. Conversion Ranking Hierarchy

Praxis defines four standardized conversion ranks for parameter-argument matching (`Analyzer::rank`):

| Rank | Classification | Description & Examples |
| :---: | :--- | :--- |
| **0** | **Exact Match** | Identical base types (e.g. `int` to `int`). Lvalue-to-reference binding where base types match and constness is preserved (`int` lvalue to `int&` or `const int&`). |
| **1** | **Promotion** | Value-preserving promotions: `bool` $\to$ `int`, `char` $\to$ `int`, `float` $\to$ `double`. |
| **2** | **Standard Conversion** | Standard numeric conversions: `int` $\to$ `float`, `double` $\to$ `int`, `long long` $\to$ `int`. |
| **3** | **Class / String Conversion** | Literal text (`Base::Text`) converting to `std::string`. |
| **-1** | **Incompatible** | Type mismatch, binding an rvalue to a non-const lvalue reference, mutating a const object, or void types. |

### 3.1 Reference Binding Rules
- Binding an lvalue to `T&` requires `bare(source) == bare(target)` and `!source.constant`.
- Binding an lvalue to `const T&` accepts both mutable and const lvalues of matching type.
- Binding an rvalue / temporary to a non-const reference `T&` is rejected (`rank = -1`).
- Binding an rvalue to `const T&` is rejected in M2 (no temporary lifetime extension).

## 4. Candidate Comparison and Best Viable Function Selection

Given viable candidates $C_1, C_2, \dots, C_k$, Praxis determines the winning candidate using pairwise comparison (`Analyzer::better`):

### 4.1 Strict Pareto Superiority
A candidate $A$ is better than candidate $B$ if and only if:
1. For all parameters $i$, $\text{rank}_A(i) \le \text{rank}_B(i)$, AND
2. For at least one parameter $j$, $\text{rank}_A(j) < \text{rank}_B(j)$.

### 4.2 Reference Constness Tie-Breaker
If two candidates have identical conversion ranks, but one binds to a non-const reference and the other binds to a const reference:
- When calling with a non-const lvalue, `f(T&)` is strictly preferred over `f(const T&)`.

### 4.3 Non-Template vs Template Tie-Breaker
If an ordinary non-template function and an instantiated template function have identical parameter conversion ranks:
- The non-template function is preferred over the template instantiation.

### 4.4 Ambiguity Detection
If after pairwise comparisons, no single candidate is strictly better than all other viable candidates:
- Overload resolution fails.
- Praxis halts compilation with an exact semantic diagnostic:
  ```text
  semantic: ambiguous overload
  ```

#### Verification Proof: `examples/m2/ambiguous_overload.cpp`
```cpp
#include <iostream>
#include <string>
void f(int a, double b) {}
void f(double a, int b) {}
int main() { f(1, 2); }
```
- In `f(1, 2)`, both arguments are `int`.
- Candidate 1 (`int, double`): ranks are `(0, 2)`.
- Candidate 2 (`double, int`): ranks are `(2, 0)`.
- Neither candidate dominates the other across all parameters.
- **Result:** Compilation fails with:
  ```text
  examples/m2/ambiguous_overload.cpp:3:68: semantic: ambiguous overload
  ```

## 5. Overload Categories Supported in M2

1. **Free-Function Overloading:** Multiple global functions with distinct parameter types.
   - Verified by `examples/m2/free_overload.cpp` (`f(int)` vs `f(double)` vs `f(int, int)`).
2. **Constructor Overloading:** Multiple constructors for a class or struct.
   - Verified by `examples/m2/constructor_overload.cpp` (Default `C()` vs Parameterized `C(int)`).
3. **Member Function Overloading:** Member functions overloaded on arity, parameter types, or const qualification.
   - Verified by `tests/m2/fixtures/member_overload.cpp` and `tests/m2/fixtures/const_overload.cpp`.
4. **Const vs Non-Const Method Dispatch:** Const objects select const member functions; non-const objects prefer non-const member functions.
5. **Template Overload Sets:** Function templates participating alongside non-template functions.
   - Verified by `tests/m2/fixtures/template_nontemplate_tie.cpp`.

---

## 6. Documented Limitations

The following advanced overload resolution features are outside the M2 boundary:
- User-defined conversion operators (`operator int()`).
- Converting constructors participating in multi-step implicit conversion sequences.
- Default argument expressions in function prototypes.
- Ellipsis / variadic parameter matching (`...`).
- Partial ordering of function templates based on template argument specialization.
